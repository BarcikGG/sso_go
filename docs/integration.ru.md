# SSO: устройство сервиса и подключение веб-приложения

Документ описывает **текущую реализацию**. Octopus в репозитории пока выступает пилотным Go-клиентом; бизнес-эндпоинты статистики и баннеров в него ещё не перенесены. Конструктор дашбордов подключается тем же способом, со своей БД, сервером, фронтом, OIDC-клиентом и набором ролей.

Интерфейс самого SSO теперь находится в отдельном проекте `sso_frontend` (React/Vite). Его Nginx публикует страницы и проксирует JSON API и OIDC в Go-контейнер `sso`. Для пользователя и подключаемых приложений остаётся один адрес SSO; cookie сессии задаёт Go и браузер не раскрывает её JavaScript. Устройство фронтенда и локальный запуск описаны в [README фронтенда](../../sso_frontend/README.md).

## Как выглядит вход для пользователя

1. Пользователь открывает приложение. Его сервер ищет собственную сессию по непрозрачной cookie.
2. Если сессии нет, сервер приложения отправляет браузер на `/authorize` SSO. В запросе есть `client_id`, точный `redirect_uri`, `state`, `nonce` и PKCE `code_challenge` с методом `S256`.
3. SSO показывает общую страницу входа. Если действующая сессия SSO уже есть, пароль повторно не спрашивается. После регистрации пользователь подтверждает email одноразовой ссылкой. Новый аккаунт имеет статус `pending`; глобальный администратор активирует его и назначает роли нужного проекта.
4. SSO возвращает браузер на callback приложения с одноразовым кодом и исходным `state`. Сервер приложения проверяет `state`, обменивает код на `/token` с `code_verifier`, проверяет ID-токен и создаёт **свою** серверную сессию.
5. При входе во второй проект повторяется короткое перенаправление через SSO. Действующая сессия SSO позволяет пройти его без ввода пароля. Доступ ко второму проекту назначается отдельно.

```text
Браузер ── cookie Octopus ──> Octopus API ──> БД Octopus: сессия, копия профиля, роли
       ├─ cookie конструктора ──> API конструктора ──> его БД: сессия, копия профиля, роли
       └─ cookie SSO ──> SSO ──> БД SSO: аккаунт, пароль, доступы, аудит
```

Cookie SSO действует только для хоста SSO. Приложение не получает её и не должно пытаться читать из неё access token. Cookie приложения также должна быть host-only (`__Host-`, `Secure`, `HttpOnly`, `Path=/`, без `Domain`), со случайным непрозрачным значением. Access/refresh-токены хранятся на сервере приложения. Для обычного API-запроса приложение читает свою сессию и **локально** проверяет право на эндпоинт или объект. SSO не вызывается на каждый запрос.

Для публикации фронта и API приложения удобен один публичный origin через reverse proxy: это упрощает cookie и защиту от CSRF. Все публичные адреса вне `localhost` должны использовать HTTPS.

## Кто владеет данными

| Данные | Владелец |
| --- | --- |
| `user_id`, email, логин, пароль, подтверждение email, статус аккаунта, имя, фамилия, аватар | SSO |
| Доступ к проекту и список его ролей | SSO; приложение хранит копию |
| Смысл роли (`manager` → `banner.read`, `banner.edit`), права на конкретный баннер или дашборд | Само приложение |
| Локальная сессия, бизнес-данные и копия полей пользователя для списков | Само приложение |

SSO хранит общий аккаунт и назначения ролей по проектам. Глобальный администратор SSO может одобрять аккаунты и менять роли во всех проектах. Роль `admin` отдельного проекта не делает пользователя глобальным администратором. Отсутствие доступа к проекту не мешает входу в другие проекты.

Роли — имена длиной до 64 символов, до десяти на одно назначение. Сейчас каталог ролей и разрешений задаётся в коде каждого приложения. Например, Octopus может определить `manager → dashboard.read, banner.read, banner.edit`, а конструктор — собственный набор для `employee`. Список конкретных разрешённых дашбордов хранится и проверяется в БД конструктора. Проверка только во фронте недостаточна.

Изменение общего профиля и пароля пользователь делает на SSO: `/settings/profile`, `/settings/password`; восстановление — `/password/forgot`. Изменение email через интерфейс пока не реализовано. Если приложение добавит свою форму общего профиля, её сервер должен сначала обновить SSO через защищённый интерфейс, затем локальную копию; в существующем пилоте для этого пока используется gRPC. Для нового приложения проще направлять пользователя на страницу профиля SSO и получать изменения через синхронизацию.

## Основные компоненты SSO

- PostgreSQL с версионированными миграциями (`migrations/postgres`). Хранит аккаунты, проекты, клиентов, заявки, доступы, сессии, хеши refresh-токенов, ключи, аудит, outbox и журнал синхронизации.
- HTTP OIDC: discovery `/.well-known/openid-configuration`, `/authorize`, `/token`, `/userinfo`, `/.well-known/jwks.json`. Authorization Code требует PKCE S256. Redirect URI сравнивается с зарегистрированным точным значением.
- Страницы `/register`, `/verify`, `/login`, `/projects`, `/settings/profile`, `/settings/password`, `/password/forgot`, `/password/reset` и центральная `/admin`. Формы защищены CSRF-токеном; сессии SSO хранятся на сервере.
- `/sync/snapshot` и `/sync/changes` — простой HTTP-канал для локальных копий каждого проекта. Доступ идёт по учётным данным зарегистрированного OIDC-клиента, а проект определяется сервером по `client_id`.
- Старые gRPC API и Kafka outbox остаются для пилота. Новому приложению для входа и копии пользователей достаточно OIDC и HTTP-синхронизации.

Код разделён на `internal/transport/httpapi` и `grpcapi` (протоколы), `internal/service` (сценарии и правила), `internal/repository/postgres` (SQL и транзакции), `internal/app` (сборка и фоновые задачи), а также отдельные адаптеры токенов, почты и Kafka. Подробные границы и правила расширения описаны в [архитектуре кода](code-architecture.ru.md).

Access token — RS256 JWT на 5 минут с `iss`, `sub`, `aud` проекта, `exp`, `kid` и его ролями. ID-токен предназначен OIDC-клиенту и имеет аудиторию `client_id`. Refresh-токен ротируется, хранится в SSO в виде хеша; повторное использование старого значения отзывает семейство. Абсолютный срок семейства — 7 дней. Ключи хранятся в PostgreSQL; после ротации старый открытый ключ остаётся в JWKS ещё 10 минут.

## Регистрация и администрирование

Новый пользователь заполняет email, логин, пароль, при желании имя и фамилию. Письмо содержит одноразовую ссылку подтверждения. Подтверждение почты само по себе **не** активирует аккаунт: глобальный администратор открывает `/admin` и нажимает «Активировать». Пользователь может заранее подать заявку на доступ к проекту на `/projects`. Администратор одобряет её с ролями или назначает роли вручную по ID пользователя. При отзыве доступа SSO отзывает refresh-токены проекта и публикует `access.revoked`; приложение должно закрыть локальные сессии этого пользователя.

Первый администратор локальной среды создаётся Compose из `SSO_BOOTSTRAP_ADMIN_EMAIL` и `SSO_BOOTSTRAP_ADMIN_PASSWORD` (последний обязательно заменить). Для существующего **подтверждённого** аккаунта оператор может назначить глобальные права:

```sh
docker compose exec -T sso /sso --grant-global-admin admin@example.com
```

Это привилегированная операторская команда. Доступ к Docker, БД и секретам SSO следует ограничивать как доступ к системе управления идентификацией.

## Как подключить Octopus или новое приложение

### 1. Зарегистрировать клиент

Выберите неизменяемые идентификаторы проекта и клиента, например `octopus`, и публичный callback. Передайте секрет через окружение команды:

```sh
SSO_NEW_CLIENT_SECRET='длинный-случайный-секрет' \
  docker compose exec -T -e SSO_NEW_CLIENT_SECRET sso \
  /sso --register-client octopus-web octopus https://octopus.example.com/oidc/callback
```

Дополнительные допустимые callback URL указываются следующими аргументами. Шаблоны и произвольные redirect URI не поддерживаются. Для каждого приложения нужен отдельный клиент и проект. Секрет хранится только на сервере приложения, в менеджере секретов. Текущая CLI-команда регистрирует нового клиента; плановой ротации существующего секрета через CLI пока нет.

### 2. Реализовать вход на сервере приложения

При начале входа сгенерируйте криптографически случайные `state`, `nonce`, `code_verifier`; положите их в короткую серверную login-транзакцию, связанную с браузером, и сформируйте SHA-256 PKCE challenge. Отправьте браузер на `authorization_endpoint` из discovery со `scope=openid profile email`, `response_type=code`, зарегистрированным `redirect_uri` и этими параметрами. Действительная сессия SSO обработает запрос автоматически.

На callback сверяйте `state` и удаляйте login-транзакцию одноразово. Код обменивайте серверным POST на `token_endpoint`, передавая `client_id`, `client_secret`, тот же `redirect_uri` и `code_verifier`. Проверяйте ID-токен по JWKS: подпись RS256 и `kid`, точный `iss`, `aud=client_id`, срок и `nonce`. Отклоняйте неизвестные алгоритмы и ключи. Для защиты API другого сервиса отдельно проверяйте access token с `aud` этого сервиса; ID-токен для этого не подходит.

Если доступ к проекту ещё не назначен, SSO возвращает OIDC-ошибку `access_pending`; покажите пользователю страницу ожидания. После успешного входа сохраните `sub` как стабильный `sso_user_id`, обновите локальную копию профиля и ролей и создайте свою серверную сессию. В браузер отправляйте только непрозрачную cookie. Логин/списки пользователей затем берите из локальной БД. Refresh-токен шифруйте при хранении у клиента, обновляйте под локальной блокировкой одной сессии и не отдавайте во фронт.

### 3. Поддерживать локальную копию

Серверное приложение аутентифицируется как зарегистрированный клиент через HTTP Basic: `client_id:client_secret`. Учетные данные нельзя передавать браузеру. Для первичной загрузки:

```http
GET /sync/snapshot HTTP/1.1
Authorization: Basic <base64(client_id:client_secret)>
```

Ответ содержит `project_id`, `cursor`, `users` (до 200) и `next_after_user`. У пользователя есть `user_id`, `email`, `login`, `name`, `given_name`, `family_name`, `avatar_url`, `roles`. Пока `next_after_user` не пуст, запрашивайте следующую страницу с `after_user=<next_after_user>&cursor=<cursor первой страницы>`. Сохраните снимок в своей БД и после его полного применения начните читать изменения с полученного курсора. При повторной полной загрузке удалите локальные назначения проекта, которых больше нет в снимке; делайте это в контролируемой транзакции или через staging-таблицу.

```http
GET /sync/changes?after=123 HTTP/1.1
Authorization: Basic <base64(client_id:client_secret)>
```

Ответ: `project_id`, `next_cursor`, `events` (до 200). Событие имеет `id`, `type`, `user_id`, `payload`. Для `access.granted`, `roles.changed`, `profile.updated` применяйте полный `payload` пользователя (upsert). Для `access.revoked` удаляйте доступ и закрывайте все локальные сессии пользователя. Для `sessions.revoked` закрывайте сессии, сохраняя назначенные роли: событие возникает после смены или сброса пароля. Повторяйте запрос, пока страница содержит 200 событий, затем опрашивайте раз в несколько секунд. **Обновление копии и сохранение курсора выполняйте в одной транзакции приложения.** После сбоя повторно полученное событие применяйте идемпотентно. SSO выдаёт только события проекта, связанного с клиентом.

Текущий журнал изменений не удаляется автоматически, поэтому приложение может догнать даже долгий простой ценой растущей таблицы SSO. Перед большой эксплуатацией нужно ввести контролируемую политику хранения, сигнал о слишком старом курсоре и повторный снимок. Пока синхронизация не дошла, отзыв роли в локальной БД приложения задерживается; это нужно учитывать в требованиях к срочному отзыву. Бизнес-эндпоинты должны проверять текущие локальные права при каждом запросе, а не полагаться только на срок жизни cookie.

### 4. Добавить RBAC приложения

В Octopus храните `sso_user_id` как внешний стабильный ключ, проектные роли и копию общих полей в собственной PostgreSQL БД. Нынешний пилот копирует email, составное имя и аватар; при переносе Octopus дополните локальную схему логином, именем и фамилией. Отдельно задайте соответствие `роль → разрешения` и проверяйте нужное разрешение в middleware/обработчике. Для прав на конкретный объект добавьте проверку по локальным бизнес-таблицам. У конструктора будет своя БД и своя таблица соответствия ролей, даже если названия ролей совпадут.

## Локальный запуск и проверки

Из корня рабочего каталога:

```sh
docker compose up --wait -d --build
```

- SSO: <http://localhost:8080/register>, админка <http://localhost:8080/admin>.
- Пилот Octopus: <http://localhost:8081>.
- Тестовая почта Mailpit: <http://localhost:8025>.

```sh
(cd sso && go test ./...)
(cd octopus_api && go test ./...)
python3 scripts/smoke.py
python3 scripts/sso_identity.py
python3 scripts/recovery.py
python3 scripts/key_rotation.py
```

`scripts/browser.py` выполняет браузерный путь в CI с Playwright. `/readyz` проверяет БД. `/metrics` показывает состояние старого Kafka outbox; метрик задержки и размера нового HTTP-журнала синхронизации пока нет.

## Перед боевым развёртыванием

Настройте HTTPS для SSO и приложений, отдельный PostgreSQL, резервное копирование и восстановление, управляемые секреты, настоящий SMTP с TLS (`SSO_SMTP_MODE=starttls` или `tls`), ограничение доступа к gRPC и БД, мониторинг готовности и ошибок. Укажите `SSO_ISSUER` как точный публичный HTTPS origin. Если SSO стоит за reverse proxy, задайте `SSO_TRUSTED_PROXY_CIDRS` списком CIDR его адресов через запятую: только от них SSO принимает цепочку `X-Forwarded-For` для ограничения попыток входа. Сам proxy должен формировать этот заголовок корректно и ограничивать размер запросов. Проверяйте часы серверов для JWT. Локальный Compose, Mailpit, демонстрационные секреты и Kafka с одним узлом предназначены только для разработки.

Реализация прошла локальные функциональные проверки, но **не проходила независимый аудит безопасности, проверку полного соответствия OIDC и нагрузочные испытания**. До запуска с реальными пользователями нужны как минимум эти проверки, процедура ротации client secret, метрики HTTP-синхронизации и решение по сроку хранения её журнала. Приложения также должны определить допустимое окно задержки отзыва доступа.
