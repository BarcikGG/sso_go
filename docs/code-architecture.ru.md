# Архитектура кода SSO

SSO разделён по ответственности. HTTP и gRPC разбирают протокол и формируют ответ, сервисы принимают решения, PostgreSQL-репозиторий читает и меняет данные. Сборка зависимостей и фоновые задачи находятся отдельно. Это практическое разделение для нынешнего размера сервиса: не создаётся отдельная абстракция на каждый SQL-запрос, но обработчики не знают схему таблиц.

```text
../sso_frontend                   React/Vite, страницы и nginx-прокси
cmd/sso
  └── internal/app                  запуск, зависимости, фоновые задачи
        ├── internal/transport/httpapi  страницы, OIDC HTTP, sync HTTP
        ├── internal/transport/grpcapi  адаптер gRPC управления
        ├── internal/service            сценарии и правила
        ├── internal/repository/postgres транзакции, SQL, миграции
        ├── internal/token              подпись и проверка JWT
        ├── internal/mail               SMTP-адаптер
        └── internal/events             публикация Kafka outbox
```

## Пакеты

- `cmd/sso` читает конфигурацию, запускает HTTP, gRPC и фоновые задачи, выполняет операторские команды (`--register-client`, `--grant-global-admin`, `--rotate-key`). В нём нет правил доступа и SQL.
- `internal/app` открывает БД, применяет миграции, создаёт сервисы и адаптеры, и управляет их жизненным циклом. Другие пакеты не импортируют `app`.
- `internal/transport/httpapi` хранит маршруты, CSRF/cookie, разбор форм, OIDC-ответы и JSON API. Обработчик вызывает сервис и переводит результат или ошибку в HTTP-ответ. В этом пакете нет SQL и шаблонов страниц.
- `../sso_frontend` — самостоятельный проект React/Vite. Он показывает вход, регистрацию, проекты, профиль и админку. Nginx отдаёт собранные файлы и проксирует `/api`, `/authorize`, `/token`, `/verify`, discovery и sync на Go-сервис. Браузер видит один origin; SSO-сессия остаётся в host-only `HttpOnly` cookie.
- `internal/transport/grpcapi` извлекает метаданные и protobuf-поля, вызывает сервис управления и переводит ошибки в gRPC-коды. Он не хранит бизнес-правила и не выполняет SQL.
- `internal/service` отвечает за сценарии: регистрация и вход (`Identity`), OIDC (`OAuth`), центральное администрирование (`Admin`), защищённое управление через gRPC (`Management`), синхронизация (`Sync`), операторские команды (`Operator`) и ограничения попыток (`Limits`). Здесь выполняются проверка ввода, полномочий, PKCE и подготовка данных для записи. Сервис не формирует HTTP/gRPC-ответы.
- `internal/repository/postgres` владеет SQL, транзакциями и версиями миграций. Методы названы по операции (`ResetPassword`, `GrantAccess`, `RotateRefresh`, `Snapshot`), а не принимают SQL-строки от вышестоящих слоёв. Запись изменений, аудита, outbox и журнала синхронизации происходит в одной транзакции.
- `internal/token` работает с RSA/JWT и зависит от узкого интерфейса хранения ключей. PostgreSQL реализует этот интерфейс; криптографический код не знает таблицы.
- `internal/events` отправляет данные в Kafka через callback репозитория, удерживающий блокировку строки outbox до ответа брокера. При ошибке запись остаётся для повторной попытки.
- `internal/mail` отправляет письма SMTP. Сервис идентификации использует интерфейс `Mailer`, поэтому не зависит от конкретного SMTP-клиента.
- `internal/security` содержит хеширование паролей и генерацию случайных токенов.

## Основные сценарии

**Вход:** React получает CSRF из `/api/ui/state` и отправляет форму на `/api/login` → `Identity.Login` → репозиторий блокирует строку аккаунта → сервис проверяет пароль и статус → репозиторий создаёт SSO-сессию в той же транзакции → обработчик ставит host-only cookie. Блокировка не позволяет смене пароля пройти между проверкой и созданием сессии.

**OIDC:** обработчик `/authorize` проверяет протокольный запрос через Fosite → `OAuth.Authorize` проверяет параметры и доступ к проекту → репозиторий записывает одноразовый код. На `/token` сервис проверяет клиента и PKCE, репозиторий атомарно потребляет код или ротирует refresh-токен, `token.KeySet` подписывает JWT. У JWT нужная аудитория проекта или клиента.

**Администрирование:** HTTP-обработчик проверяет CSRF и получает SSO-сессию → `Admin` проверяет глобальные права и роли → репозиторий меняет аккаунт/назначение и пишет аудит вместе с событиями. gRPC-интеграции могут использовать отдельный `Management` с проверкой клиентских учётных данных и пользовательского токена.

**Синхронизация:** `/sync/snapshot` и `/sync/changes` принимают учётные данные клиента → `Sync` определяет его проект → репозиторий выдаёт только данные этого проекта. События имеют монотонный курсор; запись в журнал сериализуется транзакционной блокировкой, чтобы клиент не пропустил поздний commit.

## Правила для следующих изменений

1. Новый маршрут добавляйте в нужный транспортный пакет. В обработчике оставляйте разбор запроса, cookie/CSRF и формирование ответа.
2. Проверки прав и последовательность действий помещайте в соответствующий сервис. Если сценарий новый, сначала решите, к какому предметному блоку он относится; не создавайте пакет ради одного метода.
3. SQL и блокировки строк помещайте в `repository/postgres`. Методы репозитория должны выражать операцию и сохранять её атомарность. Из сервиса нельзя вызывать `Pool.Query`, `Pool.Exec` или передавать произвольный SQL.
4. Изменения общих данных или ролей пишите вместе с аудитом, outbox и событием синхронизации. После ошибки любой записи транзакция откатывается полностью.
5. При добавлении состояния БД создавайте следующую миграцию и проверяйте обновление существующей базы, а не только чистый старт.
6. Проверяйте отказ и повтор для одноразовых кодов, refresh-токенов, ссылок подтверждения и событий. Тесты сценариев должны проходить через публичный API; внутренние функции тестируйте отдельно лишь там, где есть самостоятельное правило.

Публичный адрес SSO в Compose — `http://localhost:8080`, который слушает фронтенд-прокси. Go-контейнер доступен другим контейнерам как `sso:8080`. Для реального домена ставьте HTTPS перед фронтендом; для локального запуска браузеры разрешают `Secure` cookie на `localhost`.
