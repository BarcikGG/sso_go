# Целевая схема SSO для Octopus и конструктора дашбордов

Этот документ фиксирует продуктовую модель. Фактические интерфейсы, команды и порядок интеграции описаны в [инструкции по подключению](integration.ru.md).

## Единый вход

Пользователь открывает Octopus или конструктор. Если локальной сессии нет, приложение перенаправляет браузер в SSO. Пользователь один раз вводит логин и пароль на странице SSO; в следующем приложении действующая сессия SSO позволяет пройти вход без повторного ввода. После ответа SSO каждое приложение создаёт **свою** сессию и собственную host-only cookie. Общую cookie с access token для всех поддоменов не используем: браузерная cookie хоста SSO не отправляется другим хостам, а cookie родительского домена расширила бы область доступа.

## Аккаунт и данные

SSO — владелец `user_id`, email, логина, пароля, имени, фамилии, аватара, состояния аккаунта и проектных ролей. Пользователь регистрируется, подтверждает email, глобальный администратор активирует аккаунт и назначает доступ к проектам. На SSO также находятся страницы смены и восстановления пароля и центральная админка.

Octopus и конструктор имеют отдельные БД и сохраняют локальную копию общих полей и ролей для списков пользователей и проверок прав. Каждый проект хранит свои бизнес-данные и сессии. Копия обновляется при входе и через журнал изменений SSO. Нужды обращаться к SSO на каждом запросе API нет.

## Доступ и роли

Глобальный администратор SSO управляет аккаунтами и ролями всех проектов. Проектная роль действует только в своём проекте: один пользователь может быть `manager` в Octopus и `employee` в конструкторе. SSO назначает роли, а приложение само определяет, какие разрешения даёт каждая роль. API проверяет разрешение на каждом защищённом эндпоинте; доступ к конкретному баннеру или дашборду дополнительно проверяется по локальным данным объекта.

## Синхронизация и отзыв

SSO атомарно записывает изменение и событие для затронутого проекта. Приложение получает начальный снимок и затем опрашивает журнал с курсором. Применение событий и запись курсора выполняются в одной транзакции его БД, поэтому повторная доставка безопасна. При `access.revoked` приложение удаляет локальный доступ и завершает локальные сессии пользователя; при `sessions.revoked` завершает сессии после смены пароля, сохраняя роли. До получения события существует задержка отзыва; её допустимый предел должен быть задан отдельно для каждого проекта. Текущий журнал SSO не удаляется автоматически; перед масштабированием нужен срок хранения с протоколом повторного снимка.

## Границы первого этапа

Пилотное Go-приложение проверяет вход, локальную сессию, копию профиля и роли. Перенос бизнес-эндпоинтов Octopus с Python и конструктор дашбордов — следующие этапы. Существующие Kafka и gRPC остаются для пилота; новый проект может использовать OIDC и HTTP-синхронизацию без них. Полное соответствие OIDC, безопасность боевого контура и производительность требуют отдельной проверки перед развёртыванием для реальных пользователей.
